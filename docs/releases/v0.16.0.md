## What lands

- **Phase 0 — canonical execution.** No feature: every attempted tool call is
  forced through ONE canonical action, ONE finite decision and ONE private
  dispatch site. Its whole criterion was zero observable change, and that is
  what it delivers.
- **Phase 1 — authenticated identity.** Every ingress door mints an OPAQUE
  authenticated capability at the exact point its own authentication succeeds,
  and only there. The capability crosses the adapter, the queue and the brain,
  and the coordinator resolves it into signed identity evidence that lands in
  the SAME transaction as the action. A channel label is no longer an identity
  and a sender field is no longer a principal; a shared credential asserts a
  requester plus a subject claim, never a human.
- **Phase 2 — signed intent contracts.** An intent is a signed, versioned
  contract with a lifecycle of its own: what may be done, under which purpose,
  within which window and budget. Execution bindings tie an actor and a channel
  to one exact intent version.
- **Phase 3 — authority.** Signed, attenuated authority grants with shared
  budget accounts and a durable start authorization. Under an explicitly strict
  profile, an effectful start depends on a verified authenticated principal, one
  active signed intent and a complete active signed authority chain;
  `StartAuthorization` is the commit boundary that verifies, debits, records the
  signed start proof and — for an approved request — claims its parameters, all
  in one transaction. Only a committed start hands the coordinator an invocation
  capability. The approval document gained the `AUTORIDAD` block: who asked,
  under which contract, through which chain of principals, and the budget
  remaining WHEN THE REQUEST WAS PARKED.

Action schema 12 → 15 across the four phases. Non-strict profiles keep their
behaviour: everything above is inert until `authority.mode` is `strict`.

## BEHAVIOUR CHANGE — the closed world of strict mode

The operation-use analyzers of `read_file`, `http_fetch` and `webhook_call`
parse the argument string their TOOLS parse. A defect found by the internal
adversary in phase 3 had them parsing a JSON object no shipped tool accepts, so
a scoped grant refused every real start and an unscoped one bound nothing. With
that cured, under a **strict** profile those three tools are CLOSED WORLD —
they are the only operations with a registered analyzer, so they are the only
ones whose arguments can be proved inside a scope:

- they start only under an intent — and under every grant of the chain — that
  LISTS the resources, the data tags and the destinations they may touch;
- a `read_file` path that is not absolute is refused as unresolved, because the
  authority layer does not know the jail root the tool would join it to;
- a URL whose path is not already clean, or whose encoding is not canonical, is
  refused rather than normalized: the tool sends the URL as written, and a
  matcher cannot know which form the server will honour;
- a resource scoped by its query includes only that query; a resource with NO
  query says nothing about queries and admits any.

**And the closed world reaches further than those three.** The scope is a
property of the INTENT, not of the operation: once an intent lists any resource,
data tag or destination, every operation WITHOUT a registered analyzer refuses
too, because its arguments cannot be proved inside that scope. Today that means
`memory_note` — a `write_reversible` tool that goes through the same start door
— stops working on a profile whose intent was scoped for `read_file`. Verified
by execution, with its control: the same `memory_note` starts under an unscoped
intent. If a brain needs both, the intent must be written for both.

What the scope binds is the REQUESTED target. Where a tool goes from there is
its cage's business: the redirects `http_fetch` follows under its host
allow-list, the symbolic links `read_file` resolves under its jail. Both are
filed, not closed.

**How to turn it on**, in this order — each step is an operator act with its own
signed receipt:

```
korvun intent create-v2   --config korvun.json --file intent.json
korvun intent activate-v2 --config korvun.json <intent_id> 1
korvun authority admin-issue --config korvun.json --file grant.json --reason "…"
korvun intent bind        --config korvun.json --actor principal_brain_<name> \
                          --channel <channel> <intent_id> 1
korvun authority activate --config korvun.json --profile <profile_id> --reason "…"
```

**Three things that recipe does not tell you, and needs.** (1) On a profile
upgraded from an earlier release, the FIRST of those commands refuses until the
server has booted once: an operator act never migrates an existing store, and
the error says so. (2) `grant.json` must carry the `intent_digest` of the exact
intent version, and NO CLI verb prints it — today it is read from the store by
hand, `sqlite3 korvun.db "select digest from intent_versions where intent_id=…
and version=…"`. (3) The shape of `intent.json` and `grant.json` is documented
nowhere yet, and both parsers refuse unknown or duplicated fields, so they
cannot be guessed. All three are filed; until they are closed, this recipe is
for an operator who can read the store.

The last command prints an `activation_digest`. Put it in the config — a
top-level block, and strict mode also requires the `storage` block — with the
mode, and boot:

```json
"authority": { "mode": "strict", "activation_digest": "sha256:…" }
```

**How NOT to turn it on.** Do not add the `authority` block to a profile that
has not walked the five steps above. A profile upgraded from v0.15.1 has no
signed v2 intent at all — `korvun intent create-v2` ships for the first time
here — so its strict starts die at the FIRST gate, the missing execution
binding, with «action/sqlite: authority missing». And an intent that lists no
allowed resource grants none, so the three tools above then refuse every start
with «action: resource out of authority scope» or «action: authority use
unresolved» — the literal text the product prints; there is no short code for
either. Nothing is consumed by those refusals. Write the intent's scope first,
on a profile you can restart, and verify with one parked request before the
profile matters.

**A window this recipe opens, and how to close it.** Between step 5 and the
restart that reads the new config, the RUNNING server is still non-strict. An
approval parked in that window is born with no birth event, and the next strict
boot then reads the ledger as corrupt — which leaves the profile unable to boot
strict AT ALL, with no second activation possible. Stop the server before
`korvun authority activate`, or make sure nothing can park until it has
restarted. See the Known issues.

## Known issues

- **No public door ties a signed grant to an execution binding.** `intent bind`
  writes the binding without `grant_id`, and no other CLI verb fills it. Under a
  strict profile the applicable authority therefore resolves through the CONFIG
  CLAUSE derived from the brain's tool list, not through the signed grant chain,
  and the signed grant stays ACTIVE and unused. Observed in this release's
  manual pass: the parked start ran under `cfg_25fc…` while `grant_pedidos_root`
  sat ACTIVE beside it. The screen still tells the truth — the chain it shows is
  the one the store resolved — and nothing starts outside the intent's own
  scope, which the config-clause path verifies exactly as the grant path does.
  What is NOT reachable today is delegation: attenuated child grants, shared
  ancestor budgets and depth limits are implemented and tested, and an operator
  has no way to put one in the path of an execution.
- **A strict approval is resumable only while its approval window lasts, and a
  non-strict one only while its ingress evidence lasts.** In phase 3 the strict
  approved resume judges the ingress capability's expiry at the instant the
  request was PARKED, read from the signed pending snapshot, while a disabled
  principal or a moved binding is judged at the start. The phase-1 legacy claim
  was NOT changed: it has no signed park instant to read, so it still judges
  expiry at the claim, and with production's five-minute ingress TTL a
  non-strict approval decided later than that refuses with
  «identity: authenticated ingress expired». The asymmetry is deliberate.
- **Under an activated profile every strict start re-verifies the whole
  approval-birth ledger and every `approvals` row.** It is LINEAR in the
  profile's lifetime approvals. No bound, no cache, no measurement at scale:
  filed by name.
- **A NON-STRICT BOOT over an activated profile poisons it, permanently.** The
  birth ledger is appended only by a store armed with the activation digest, and
  only a strict boot arms it (`app.Build` calls `PrepareStrictAuthority` under
  `cfg.StrictAuthority()`). So a boot whose config has lost — or has not yet
  gained — the `authority` block parks approvals with no birth event, and the
  next strict boot reads the ledger as corrupt. That is not merely «nothing
  starts»: it is boot-fatal, `app.Build` returns the error and the server does
  not start at all, and there is no remedy, because a second `authority
  activate` for the same profile is refused. The release's own recipe opens this
  window between the activation and the restart (see «How NOT to turn it on»).
  Nothing in the product prevents the state and nothing repairs it. An earlier
  draft of these notes said no production door could create it; that was false,
  and the internal adversary proved it with two real store instances over one
  file.

- **`internal/action/sqlite` takes about 300 s locally under `-race`**, and the
  Windows runner has run that package between 2.5 and 4 times slower, against a
  30-minute ceiling. The margin is real but it is not wide.

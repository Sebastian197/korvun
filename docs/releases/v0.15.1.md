A patch over v0.15.0 that cures the three P1 findings of the seventeenth
external pass — the one that judged the tree after v0.15.0 shipped, whose
report is not in this repository — and folds in P2-4 of the v0.15.0 Known
issues, which comes from the fifteenth pass, the one that vetoed the v0.15.0
tag over `1817dd4`. A2 and A3 are
cured as classes; A1's class is not wholly cured: a restore committed by
another connection after the claim commits, while the action is still
APPROVED, still yields a second execution (Known issues).

## Block A — what a claim, a webhook call and the crash pass may say

- **A purge that does not hold is refused.** The approval claim purges
  `canonical_params` and used to trust the UPDATE's row count. It now re-reads
  the column inside its own transaction, after the purge and before the
  commit. A cell that is not the empty string after the purge, or a purge that
  touched more than one row, refuses with `ErrApprovalEvidenceCorrupt` and the
  whole transaction rolls back; a purge that touched no row is
  `ErrApprovalClaimSkipped`, after the claim's authority re-read, which may
  name `ErrApprovalNoLongerApproved` first. Under a trigger that restores the column, both claims are refused and
  nothing runs. Its scope is the claim's own transaction: a restore committed
  by another connection AFTER the claim commits is not stopped (Known issues).
- **One class per cell the claim reads.** A NULL, a value that does not convert
  or a status/state outside its domain, in any cell the claim reads inside its
  transaction except the nullable `principal_id`, is corrupt evidence. The gap
  block A left — the claim naming every non-NotFound error of `approvalTx`
  corrupt, a driver failure included — is X1, cured by block B: a read that
  failed because the store did not answer is `ErrApprovalUnreadable`, and only
  a row that was read and does not convert is corrupt. The stored effect-class domain is the
  sealed enum plus the «unclassified» placeholder that envelopes carry when no
  classifier is wired.
- **Only a 2xx answer is success for `webhook_call`.** The tool observes
  `GotConn`, the one signal that proves no request byte left before it:

  | Wire fact | Closes on |
  | --- | --- |
  | no connection obtained (dial refused, handshake never completed, shield, context ended first) | FAILED (`ErrNotSent`) |
  | connection obtained, no answer | OUTCOME_UNKNOWN (`ErrDeliveryUnknown`) |
  | the receiver answered, not with a usable success (status < 200 or > 299, a refused redirect, an unreadable or oversized 2xx body) | OUTCOME_UNKNOWN (`ErrEffectDelivered`) |
  | the receiver answered 2xx | SUCCEEDED |

  The approved path and the brain path both classify with the same table
  (`CloseStateAfterRun`). This cures v0.15.0's P2-4: a handshake that never
  completed now closes FAILED even when the run ended on a deadline.
- **`ErrEffectDelivered`'s text says what is true of every member:** «the
  receiver answered and the answer was not a usable success».
- **Log field renamed, declared.** The brain's cage-denial log record carried a
  boolean `delivered`; it now carries `delivery` with one of `response_read`,
  `unknown`, `not_sent`, `not_observed`. An operator's log query on
  `delivered` stops matching. No consumer of the old field exists in the
  repository.
- **The crash pass closes only what it owns.** The crash-orphan UPDATE now
  excludes `AUTHORIZED` in its own WHERE, so a row that became AUTHORIZED
  between the pass's SELECT and its UPDATE (a tool now running) is no longer
  closed FAILED with a crash receipt.
- **A moved row is named before a moved law.** The claim compares the caller's
  snapshot before judging the law, so a row that moved is no longer published
  `invalidated`. Reachable by out-of-band tampering only.

## Block B

Cures seven P2 findings, their sisters, and X1, routed here from block A.
Five of the seven come from the fifteenth pass's Known issues: P2-6, P2-7,
P2-8, P2-9 and P2-10. Two — P2-1 and P2-2 — carry the numbering of the
seventeenth pass, whose report is not in this repository; they were built from
the director's description of it and from the code, and block B's paper records
that as an open question. Of the fifteenth pass's remaining P2s, P2-4 is block
A's, above, and P2-5 and P2-11 are cured by nobody here: both are corrections
of what was CLAIMED, and they are block C's, below.

- **The approval doors answer only the machine that runs Korvun.** The
  approvals routes and the console's `/message` refuse any peer that is not
  loopback with the name `loopback_only`, before any seam is called, and with
  no opt-in. The screen's copy says so in the operator's words.
- **One class per failed read of an approval row.** A row that was read and
  does not convert — text in an integer column, a time that does not parse, a
  NULL where the destination is not nullable, a `schema_version` outside the
  int32 range — is `ErrApprovalEvidenceCorrupt`; a read the store did not
  answer (a cancelled context, a driver failure, a statement that cannot be
  prepared) is `ErrApprovalUnreadable`. Never both. The doors: `GetApproval`,
  `ListApprovals`, the decide, the expiry sweep's reads, the detail, the
  re-read and the claim's first read. Two reads of the same table stay
  outside, both filed for v0.15.2: `ListPendingApprovals`, which skips and
  counts the row it cannot scan and names it with an EMPTY id, and
  `GetApprovalByAction`, which returns its read error with neither class.
- **The receipt seals a mark, never an empty reference.** When the approval
  row cannot be used at the moment of sealing, the receipt seals one mark of a
  closed list (`corrupt:row_scan`, `corrupt:decision_at`,
  `corrupt:decision_principal`, `corrupt:decision_verb`,
  `corrupt:approval_missing`, `corrupt:status`, `unreadable:driver`), and
  `receipt verify` and `ledger check` fail such a receipt by name
  (`approval_evidence_corrupt`, `approval_evidence_unreadable`, and
  `approval_evidence_unknown_mark` for anything that is neither a digest nor a
  listed mark), also after a prune.
- **A driver failure in the transition is not «already closed».** It is
  `ErrApprovalWriteFailed` and is published as `unavailable`;
  `already_closed` is left for an action that really moved.
- **The law read is the approval's own.** `current_law_digest` comes from the
  approval's own brain in the detail, in approve and at the claim's gate.
- **The screen judges the answer's shape.** Only an exact success paints
  «Ejecutada»; a 200 it cannot read, a digest that moved under the operator's
  eyes, a malformed id and a non-loopback origin each get their own text.
- **The operator's doors validate the approval id by shape**, and the stored
  fields that `korvun approvals show` and `approvals list` print on stdout, and
  that the screen renders, are escaped. Nothing wider is claimed: the CLI's
  error lines on stderr carry stored bytes raw, and so do the failure lines
  `receipt verify` and `ledger check` print on stdout. Both are filed for
  v0.15.2, each with its own capture.
- **`-h` and `--help` answer** in approvals, ledger, receipt, intent and grant.
- **Wording.** The `already_decided` message no longer claims «nothing ran
  twice»: the refusal knows the request is closed, not what ran.

## Block C

No production code. It corrects what the project CLAIMED, in the repository and
on the website, and adds a guard so one class of the drift cannot come back.

- **P2-5, corrected, not cured.** The v0.15.0 notes said the digest travelling
  from the window is the one the operator typed. It is the full digest the
  detail served; the six characters typed only arm the button. The behaviour is
  unchanged.
- **P2-11, scoped.** The approvals ceremony record is narrated, not evidenced:
  nothing in the tree binds its outputs to a real run. The canto, the spec and
  the v0.15.0 notes now say so.
- **The SBOM promise narrowed to what a release ships:** an SPDX SBOM for each
  of the six headless archives; the three desktop packages ship without one.
- **Approvals described as opt-in** (`approvals.enabled`), with the park that
  falls closed to the denial, and single consumption with its two declared
  limits.
- **What was filed «for v0.15.1» and is not delivered** now says so, and is
  listed below.
- **A new guard**, `website/scripts/check-current-release.mjs`, inside
  `make website-check`: five current-release claims must name
  `releaseFacts.tag`, each exactly once — the README's download line, its
  current-release line and its release-notes link, and the current-release row
  of each releases table, EN and ES, where the href's tag is judged as well as
  the link text. A missing claim fails; it is not read as a matching one.

## Known issues, filed to v0.15.2

- **Single consumption does not hold against a restore committed while the
  action is still APPROVED.** A second connection that writes the original
  bytes back into `approvals.canonical_params` after the claim commits, while
  the action is still APPROVED (a first execution still running, one whose
  close failed, or a claim followed by a crash before the close), followed by
  a second `ExecuteApprovedAction` (or `korvun approvals execute`), claims
  them again: two executions (`runs=2`). The in-flight shape was reproduced by
  the adversary of block A's diff pass, identical at the train's base
  `61ae582` and under the cure; the failed-close and crash shapes by the
  adversary of block C's pass. A restore after the action closed gets no
  second run. Scoped and filed by the director's decision, not redesigned.
- **A deterministic error inside the purge is published unreadable.** A trigger
  `RAISE` or a NOT NULL constraint that fails the purge surfaces as
  `ErrApprovalUnreadable`, a store that did not answer, although it is
  permanent. Pre-existing; declared in block A's canto, no reproduction
  captured.
- **`ledger check` fails the earlier life of a reused action id.** With a
  reused `action_id`, the verifier reads the new life's action row as the old
  one's and fails the earlier receipt with `approval_mismatch`. Reported as
  pre-existing at base `61ae582` in block B's paper (row P2-6); capture
  pending.

- **Filed before, not delivered by v0.15.1, now unscheduled** (`SECURITY.md`):
  a failure name that may describe a disagreement when ANOTHER receipt of the
  chain does not parse; the four limits that need an external anchor or a
  scanning verifier; and verifying the downloaded GoReleaser binary against a
  pinned checksum so the release chain fails closed.
- **A confirmed park can return an error.** `CreateApprovalRequest` returns
  the error of the post-commit retention sweep; the brain then falls closed to
  a denial over an action that stays `PENDING_APPROVAL`. Pre-existing; by
  reading of the code, not executed.

**Forward-compatibility note, not a defect:** an effect class written by a
newer binary without a schema bump would fall outside this binary's stored
domain and read as corrupt evidence: it fails closed and executes nothing.
Predicted, not executed.

# Korvun v0.14.0 — Beta: the ledger and the verifiable receipts

The fourth release of the Execution Trust Layer era (Etapa 4 of 10).
Korvun now keeps a book of records: every terminal action outcome —
denied, shadowed, succeeded or failed — leaves a canonical receipt,
signed with Ed25519, on an append-only hash chain, born in the SAME
transaction as the outcome itself. The operator re-judges that book
offline, against the file, with seven named checks — and the design
confesses its limit out loud: the ledger is **tamper-evident, never
"immutable"**, because the operator controls both storage and keys.
The engine stays invisible in the app: today's flows do not move one
pixel.

## The receipt is born with its row

A receipt is a digest-only record of one terminal outcome: what was
requested (action digest), under which contract (intent digest), by
which law (decision digest with the pinned policy), what class of
consequence, and what came out (outcome + an on-the-fly result digest —
the raw result NEVER touches the disk; only its fingerprint does).
Denied and shadowed attempts receipt at the gate; executed ones at
their terminal close — always inside the outcome's own transaction,
through a domain API with no update or delete paths. An append that
cannot happen fails the WHOLE record closed: an unreceipted effect
cannot exist. Under a 60-goroutine race hammer, the chain sequence
never duplicates and never gaps.

## The chain and the ink

Receipts link hash to hash from a documented genesis, one monotonic
sequence per partition. Each one is sealed live — canonical bytes,
SHA-256, Ed25519 with the profile's ACTIVE key — and the private seed
lives beside the store in a 0600 file whose permissions are verified on
every boot. Keys rotate atomically (retire-and-activate, one
transaction; `korvun receipt rotate-key`); retired keys are kept
forever, so **each era of the chain verifies with the key of its era**
— and a receipt claiming to be sealed outside its key's lifetime is
denounced by name. Retired ink never signs again: a stale key file
after a rotation crash is refused closed, with the staged seed named
for recovery.

## The operator's verifier: seven checks, every failure named

`korvun receipt verify` re-judges one receipt offline — trusting
nothing, not even its own base: canonical roundtrip through the
birth-fuzzed strict parser, hash recompute, signature against the
REGISTERED public key by its `signing_key_id`, the key's validity
window, the chain link to the predecessor, and coherence with the
action row itself. `korvun ledger check` walks a whole partition:
structure first (a deleted receipt is denounced by its hole as
`chain_seq_gap` with the missing position; a cloned position as
`chain_seq_duplicate`), then every link through the same ladder — the
FIRST broken link stops the verdict with its receipt id and its
reason. There is no generic "invalid" anywhere: every refusal carries
its name.

## The forgery, caught in the act — and the limit, confessed

The release was accepted through the ceremony on the director's real
profile. His own receipt verified with all seven seals; then, on a
DISPOSABLE copy of his store (the real book receives no sabotage,
ever), a forged outcome was caught in triplicate — `hash_mismatch`
with the two hashes face to face, `signature_invalid`, and
`custody_mismatch` against the action row; a mid-chain deletion was
denounced with its exact position; and the ceremony's final act showed
the documented limit ON PURPOSE: truncating the chain's TAIL leaves no
hole to detect. That is the honest scope, now written into SECURITY.md
and governing every public line of this project: with the signing key
resident on the same machine, the ledger proves tampering by anyone
without the active key — it does not promise immutability against the
machine's own owner. Korvun says "tamper-evident" and means exactly
that.

## Compatibility

Store migrations v4→v5→v6 (signing keys, receipts) run automatically
on the anti-zombie runner: an aborted step leaves the previous schema
intact and the next boot completes it. Receipts are EXEMPT from the
evidence retention prune — the book outlives the rows it attests. The
hot path re-measured with the ink inside: ~1.25 ms per governed action
(sealing adds ~0.4 ms), under the 5 ms ceiling with ~4× margin. The
exterior is untouched: transcript, feeds, SSE and metrics receive no
receipt material, no key material, no signature bytes — digests and
finite labels only, pinned by a negative sweep against the run's real
secrets. Existing configs need nothing: the same binary, the same
files, now with a book of records underneath.

## Erratum — added 2026-08-31 (external review)

An independent external review of this release surfaced three
reproducible defects and one over-broad promise, fixed in v0.14.1
without rewriting the text above (history stays as published):

1. The verifier's CLI opened the store through the full lifecycle door
   (migrations, crash recovery, retention prune) — so a `receipt
   verify` beside a live server could close its in-flight actions, and
   a consult could silently migrate a profile. v0.14.1 gives every
   consult a true read-only door (no migration, no recovery, no file
   creation, a write-refusing connection).
2. A receipt whose action row had been legitimately pruned by
   retention failed verification with a misleading `custody_mismatch`.
   v0.14.1 degrades the absent row to the named non-fatal note
   `action_row_absent` — the digest-sealed receipt is the evidence
   that survives, by design.
3. `make cover` swallowed test failures. Fixed with real exit codes.
4. The phrase "an unreceipted effect cannot exist" above is broader
   than the design guarantees: atomicity holds INSIDE the store; an
   EXTERNAL effect completed just before a failed terminal close is a
   real, documented window until stage 6's reconciliation. README and
   SECURITY.md now state the scoped promise.

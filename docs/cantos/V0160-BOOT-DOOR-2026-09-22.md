## 2 · How this cure could itself break something

- **It turns a profile that RAN into one that does not.** Before the door, a
  non-strict boot over an activated profile started, with the poisoning risk.
  After it, that boot is refused. If the operator cannot produce the activation
  digest, the refusal is a dead end — and activation is one-way: no verb
  deactivates, and a second activation of the same profile is refused.
  **This is exactly what the first shape shipped**, because the refusal asked
  for a digest the reader had just read and did not print. The adversary proved
  it with the compiled binary. Cured: the reader returns the digest beside each
  profile and the message prints it, so the refusal repairs itself.
- **It could call a legitimate state corrupt.** `authority activate` takes any
  profile id and refuses only a repeat of the same one, so two activation roots
  on one store is a state the CLI creates. The first shape called it
  `ErrAuthorizationSnapshotCorrupt` and lost its own sentinel on that path.
  Cured: both roots are reported, with both digests, under the refusal's
  sentinel.
- **It could fail OPEN.** A reader whose job is to refuse must never answer
  «nothing is activated» because it could not read. Every error arm returns the
  error; the nil-store arm refuses instead of returning nil, as its sibling
  `PrepareStrictAuthority` does.
- **It could cost a cheap rejection.** `Preflight` opens no store by design, so
  a reload that drops the `authority` block now fails at the cutover instead of
  before it. Bounded by the supervisor's rollback, which restores the previous
  config and never persists the bad one. Declared, not cured.

## 4 · The class, not the instance

The fault's class is «a door that operates on an ACTIVATED profile without
arming itself, and therefore without the ledger's guarantees». Its members,
each named:

- **`app.Build` serving non-strict** — the only one that can PARK, and so the
  only one that can create an approval with no birth event. **CURED here.**
- **`korvun approvals reject`** — opens the store sealed and does NOT arm
  (`internal/cli/approvals.go` arms only when the verb is `approve`). A reject
  closes a parked action and executes nothing, so it cannot create the poisoned
  state; what it skips is the activation verification a strict profile would
  otherwise run. **FILED by name, not cured here.**
- **`korvun approvals list` and `show`** — read-only doors that do not arm and
  do not print authority. **FILED by name.**
- **`korvun intent`, `grant`, `authority`, `receipt`** — eighteen sealed opens
  across the CLI, none of which arms. They write intents, grants and receipts,
  never approvals, so none can create the state. **FILED by name.**
- **The desktop e2e harness** — parks through the production door under an
  isolated temporary HOME and is only compiled in CI. Not a production door.

Nothing of this class is cured in silence: one member is closed, the rest are
listed above and carried into the release notes' Known issues.

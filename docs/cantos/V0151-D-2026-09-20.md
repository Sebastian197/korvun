## Guarantee

For an approval POST, the desktop screen paints `executed` or `failed` only
when a status 200 response contains all of these fields:

- a matching `outcome`;
- a `digest` shaped as `sha256:` followed by 64 lowercase hexadecimal digits;
- a non-empty string `result`; and
- a `receipt_id` shaped as `rcpt_` followed by 32 lowercase hexadecimal digits.

A missing, empty, wrongly typed, or malformed required field produces the
existing unrecognised-response state. The screen does not paint `Ejecutada` or
`El intento falló` for that response.

This change does not alter the `rejected` response contract.

## The audit of this train, and what it changed (2026-09-20)

This train was written by the external executor and audited here, by the
internal adversary, in ONE scoped pass over its diff. The pass returned **VETO
MANTENIDO**: two P2 [PRODUCT], one P2 [INSTRUMENT] and five P3. Everything it
found is cured in this same tree, and what follows is what the cures changed —
including the two sentences of this canto that were false.

### [PRODUCT] The `rejected` path lost a guard it had, and this canto denied it

The first version moved the type guard for `digest` and `result` BELOW
`reject`'s early return, so a rejected answer carrying `digest: 7` or
`result: {a:1}` — refused on master — painted «Rechazada». The adversary
captured both behaviours, on master and on the branch, with the same probe.
The sentence «This change does not alter the `rejected` response contract» was
therefore false, and is replaced by what the code now does: the guard is back
above the early return, and two mould rows watch it. Probing mutation **m-d7**
(move the early return above the guard again) reddens exactly those two rows.

The receipt's SHAPE is deliberately NOT required for `rejected`. Requiring it
reddens an approved mould that proves the screen ESCAPES a hostile receipt
where it prints it — a receipt that no longer reaches the paint would leave
that guarantee without a subject. The audit's P3-4 (a `rejected` answer whose
`receipt_id` is empty prints «Recibo » bare, under a title that says «con su
recibo sellado») is therefore NOT cured here: it is behaviour inherited from
master, reachable only from a row corrupted outside the screen, and it is filed
for v0.15.2 in `docs/HANDOFF.md`. The godoc no longer claims otherwise.

### [PRODUCT] The response's digest was judged by shape and thrown away

The first version validated `b.digest` and then painted `detail.digest`, the
value the screen already held: an answer about ANOTHER action, well shaped,
painted as this one's. The adversary captured it — a response carrying
`sha256:bbbb…` painted «Ejecutada» over the detail's own digest.

Cured: `judgeDecision` now takes the digest the screen SENT with the request,
refuses any answer whose `digest` is not identical to it, and the screen paints
the digest the ANSWER carried, which is now provably the same string. Mould:
two rows, one for `executed` and one for `failed`, each with a well-shaped
digest that differs from the one sent. Probing mutation **m-d6** (drop the
identity check, keep the shape check) reddens both.

### [INSTRUMENT] The 2xx rows stopped watching the status guard

The two rows that send a success body with status 201 and 202 carried
`receipt_id: 'rcp_x'`, which the new receipt guard refuses on its own — so
after the cure they passed even with the status guard widened to any 2xx. The
adversary proved it with that mutation: three rows red on master, one on the
branch, and none of them the approve verb this train is about. The rows now
carry an EXACT body — minted receipt, matching digest, non-empty result — so
only the status can refuse them. Probing mutation **m-d4** (widen the guard to
`status < 200 || status > 299`) reddens all three.

### [INSTRUMENT] `outcome` was never proved to be judged by equality

Nothing in the tree reddened when `=== 'executed'` became `startsWith('exec')`.
A row with `outcome: 'executed_partially'` now watches it, and probing mutation
**m-d5** reddens it.

- **A `rejected` answer with an empty `receipt_id`** prints «Recibo » bare

  a blank result line. The guarantee says «non-empty string», which is what the
  code does; recorded so the next train can decide whether it wanted content.

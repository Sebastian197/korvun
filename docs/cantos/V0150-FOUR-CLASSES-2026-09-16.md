Train `v0150-four-classes`, base `9af9ff2af3cdcf404420c57910ee055e2d44e618`.
Director's order of 2026-09-16: cure the four findings AS CLASSES and publish,
without going back to the external reviewer before the tag.

Each of the four is a cure whose previous form closed the case the reviewer
named and left the class open. That is the pattern this train attacks — and the
internal adversary then found the same pattern one level up, in the train
itself: see §3.

## 1. What the train does

- **The claim judges every column `action.Approval` carries.** The P1-1 cure
  re-read `status` and the action's `state` inside the claiming transaction,
  because the review named those two columns. The rest of the row — the
  digests, the law pin, the window, the decision fields — was read by the caller
  BEFORE the transaction and never compared inside it. Now the caller hands the
  claim the snapshot its prechecks read
  (`ClaimApprovalParamsUnderDigest(..., seen *action.Approval)`), and the claim
  compares that snapshot against the row ITS transaction read, column by
  column, refusing with `ErrApprovalMovedUnderTheClaim` and consuming nothing.
- **The escape alphabet reserves its own bracket.** Every escape the approvals
  screen prints reads `<U+XXXX>`, so untrusted bytes containing `<` could spell
  one: the literal text `<U+2060>` read exactly like the escape of a real
  U+2060. `<` now renders `<U+003C>`, and the pair disappears. Two sibling
  fields that reached the DOM raw — the law digest and the readable expiry —
  go through the escape too (§3, F7).
- **ONE function classifies the outcome.** `tool.CloseStateAfterRun` is the only
  place that decides what a tool run closes on, and both execution paths call
  it. The two copies had already disagreed once about a bare deadline.
- **The close does not ride the caller's context, and AUTHORIZED is unknown.**
  Both paths close through `context.WithoutCancel(ctx)` — and the approved path
  re-reads its receipt on the same context — so a cancellation while the tool
  runs can no longer leave an irreversible effect with no ledger row. The
  recovery pass closes an AUTHORIZED orphan `OUTCOME_UNKNOWN` instead of
  `FAILED`: its tool was running when the process died, so nobody observed the
  effect. The CLI's «the operator's loopback right» comment is scoped down in
  the same commit.

previous life» and asserted FAILED + `crash_recovered`:

actually guards — never re-executed, the postponement counted, exactly one

accepts only DENIED, SHADOWED and AUTHORIZED, so with AUTHORIZED gone the
FAILED pass had no reachable state through the public door. It is still
reachable on disk — an older binary, or a state this code does not know — so
`TestRecovery_aLegacyNonTerminalStillClosesFailed` forces `PREPARING` behind
the API and pins that the pass still closes it.

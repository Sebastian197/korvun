# Piece 3, Phase 1: Authenticated Identity Design Spec

> **Status:** draft for pre-test adversarial review.
> Governing material: `CLAUDE.md`, ADR-0010, ADR-0017, ADR-0021,
> ADR-0028, ADR-0033, ADR-0038, and
> `design-drafts/2026-09-19-pieza-3-identidad-intencion-autoridad-codex.md`.
> This phase uses only the Go standard library and existing `internal/`
> packages. It adds no dependency.

## Goal

Bind each accepted ingress to the shared credential or authenticated session
that the production adapter actually observed. Carry that opaque fact through
the router queue, resolve requester, actor, and responsible principals before
an action can start, and persist signed identity evidence with the action.

The phase does not claim personal identity. A Telegram or Discord subject is
an account claim inside a bot session. A webhook sender is payload data. A
console bearer and a local CLI profile prove control of those capabilities,
not which person used them.

## Current-tree adaptation

The 2026-09-19 paper assumed Phase 1 would precede the other Piece 3 phases.
The current base is `551f9770e47709446f7d14229aa0f931a34b2ff3` and has Phase 0
and Phase 2 already integrated. This changes the implementation points:

- Phase 2 owns schema 13. This phase migrates 13 to 14. It does not rewrite,
  sign, import, or reinterpret Phase 2 intent rows or legacy identity rows.
- Phase 0 owns action birth and start in `internal/action/executor`. Identity
  is therefore bound in `executor.Submission` and judged by the coordinator.
  `runTool` remains a presentation adapter.
- Phase 2 `execution_bindings` select intents. Phase 1
  `principal_bindings` authenticate ingress. Their names and duties remain
  separate.
- Phase 2 intent enforcement remains deferred to Phase 3. Adding identity
  cannot make an intent grant authority.
- The current legacy `ProvenanceRegistry`, `ResolvePrincipal`, evidence table,
  and optional identified-recorder seam remain readable and callable for
  compatibility. Production composition stops treating them as proof of
  authenticated ingress.

## Functional requirements

- **FR-ID-01.** `internal/identity` defines the v2 domain. Principal kinds are
  `human`, `agent`, `workload`, and `external_system`. Existing legacy kinds
  remain readable in their existing rows. `operator` is a configured role,
  not a claim that a personally identified human was observed.
- **FR-ID-02.** `identity.AuthenticatedIngress` is opaque. Its zero value is
  invalid, its fields are not exported, and it has no JSON representation.
  Only an issuer obtained from the app-composed resolver can mint a value the
  same resolver accepts.
- **FR-ID-03.** An ingress contains a request id, adapter instance id, binding
  id and generation, requester principal id, credential class, issuer,
  method, observed time, optional expiry, subject namespace, subject claim,
  and a digest of the allowlisted claims. It cannot carry a token, header,
  prompt, message parts, or full payload.
- **FR-ID-04.** A channel adapter attaches the ingress only after its real
  authentication cut. Generic webhook issuance follows `authGate`. Telegram
  polling issuance occurs inside the authenticated bot callback. Telegram
  webhook issuance follows the secret-header comparison. Discord issuance
  occurs inside an authenticated Gateway session. Console issuance follows
  the console bearer. CLI operator acts use an explicit local-profile issuer
  after the sealed operator store is open.
- **FR-ID-05.** `Envelope` can temporarily carry the opaque ingress between
  an adapter and the router, but JSON marshal and unmarshal cannot expose or
  populate it. Sender, display name, channel label, `Meta`, prompt, and body
  fields cannot mint or alter it.
- **FR-ID-06.** The router queue carries an `inboundWork` containing both the
  envelope and the ingress. The brain worker passes that ingress through an
  authenticated-brain seam. It is not reconstructed from the envelope and it
  is not transported only through `context.Context` across the queue.
- **FR-ID-07.** The executor resolver derives requester from the ingress,
  actor from the app-composed workload registry keyed by the executor's fixed
  brain name, and responsible from that workload registration. Model output
  cannot provide any of the three.
- **FR-ID-08.** One ingress may produce several tool calls. Each action gets a
  fresh evidence id and signature while retaining the same request,
  requester, binding, generation, adapter instance, and observed fact.
- **FR-ID-09.** Missing, zero, unknown, expired, request-mismatched,
  channel-mismatched, binding-mismatched, generation-mismatched, or corrupt
  ingress refuses a production v2 action before approval birth,
  authorization recording, claim, or tool dispatch. The stable sentinels are
  `ErrIdentityEvidenceMissing`, `ErrIdentityBindingMismatch`,
  `ErrIdentityEvidenceExpired`, and `ErrIdentityEvidenceCorrupt`.
- **FR-ID-10.** The store rechecks requester, actor, responsible, active
  binding, and generation inside the transaction that records an authorized
  action or parks an approval. A committed principal disable wins over an
  earlier in-memory resolution. The refusal class is
  `ErrPrincipalDisabled`.
- **FR-ID-11.** Approved execution verifies the stored v2 evidence, signature,
  requester, actor, responsible, active binding, generation, request binding,
  and expiry inside the existing claim transaction before parameters are
  purged. The verification uses transaction-scoped key reads. Existing claim
  sentinels, single-consumption behavior, close semantics, `WithoutCancel`,
  and `OUTCOME_UNKNOWN` recovery remain unchanged.
- **FR-ID-12.** Identity evidence v2 is signed under
  `korvun.identity-evidence.v2` with the active profile Ed25519 key. Principal
  events are signed under `korvun.principal-event.v1`. Existing registered
  keys verify old acts; retired keys cannot sign new acts.
- **FR-ID-13.** The app boot registers configured principals, workloads, and
  principal bindings idempotently after the profile signer is available. An
  equivalent existing row is a no-op. An incompatible row is boot-fatal and
  is never overwritten. The app uses a fresh private adapter-instance seal
  on each construction, so a capability from another instance cannot pass
  even when the persisted configuration generation is unchanged.
- **FR-ID-14.** Schema 13 migrates transactionally to 14 by adding
  `principals`, `principal_bindings`, `identity_evidence_v2`, and
  `principal_events`. It also adds nullable-by-era receipt attribution
  columns for requester, actor, responsible, identity status, the
  identity-evidence digest, and the birth-snapshot digest. Existing tables
  and rows are not copied into the four new tables.
- **FR-ID-14a.** The same migration adds an era marker, evidence digest,
  canonical signed evidence, signing-key id, and signature snapshot to
  `actions`. Legacy rows receive era zero and empty snapshots. A v2 action
  writes era two and the exact signed snapshot in its birth transaction.
  A row is legacy only when the marker is zero and every snapshot field is
  empty. Any other tuple is identity-bearing; it is valid only when the
  marker is two and every snapshot field is present and verifies.
  Recovery trusts attribution only after canonical, digest, key, and signature
  verification; mutable convenience columns are never an attribution oracle.
- **FR-ID-15.** `identity_evidence_v2` commits in the same transaction as the
  action and decision. Approval birth includes its v2 evidence in the same
  born-whole transaction. An evidence insert or validation failure rolls all
  of those rows back.
- **FR-ID-16.** Historical v1 and v2 receipt bytes remain unchanged. Every
  terminal path for a new v2 identity action, including deny, shadow, unknown
  tool, undeclared effect, finish, rejection, and recovery, receives a v3
  receipt. A verified v3 receipt signs `identity_status=verified`, requester,
  actor, responsible, the canonical identity-evidence digest, and the exact
  birth-snapshot digest. If recovery finds the birth snapshot corrupt, it
  signs `identity_status=corrupt`, the exact digest of the encountered
  snapshot tuple, an empty evidence digest, and empty attribution instead of
  legitimizing altered ids. Every signed v3 term is stored explicitly and
  survives a database reopen. It never embeds canonical evidence,
  credentials, headers, prompt text, or payload bytes.
- **FR-ID-17.** The legacy resolver and recorder remain a compatibility
  profile. They are not used by app production wiring after this phase, and a
  v2 request never falls back to legacy identity. The supported no-store mode
  still mints, carries, and resolves opaque ingress in memory and preserves
  existing execution behavior without pretending to create durable evidence.
  Durable disable and binding rechecks apply when the action store exists.
  A strict storage prerequisite remains Phase 3 work under the director's
  storage decision.
- **FR-ID-18.** Identity-related logs, Prometheus output, and live-view frames
  contain finite ids, classes, methods, and outcomes only. The v2 evidence
  serializer and those sinks never include secret values, authorization
  headers, webhook secret headers, prompt text, message parts, or raw payload.
- **FR-ID-19.** Router shutdown keeps its current cut. Work already acquired by
  the old brain retains its R1 ingress and may finish under R1. Work still
  waiting in the old queue is cancelled with that router and is never moved to
  the replacement. Neither case is reconstructed under R2 or generation 2.
- **FR-ID-20.** Recovery closes v2 `AUTHORIZED` and claimed `APPROVED` actions
  exactly once as `OUTCOME_UNKNOWN`, using only the verified signed action
  birth snapshot for v3 receipt attribution. Missing or unreadable full
  evidence never blocks this safety close. A corrupt birth snapshot produces
  a corrupt-status v3 receipt without attribution. Mutable resolver
  configuration is never consulted.
- **FR-ID-21.** Boot and every durable start verify each participating
  principal projection against its latest signed principal event. A projection
  rewound from disabled revision 2 to active revision 1 while the signed
  disable event remains is `ErrPrincipalEvidenceCorrupt`, never re-enabled.
  Raw deletion plus rollback of both projection and signed history is part of
  the database-rollback limitation, not something this self-contained store
  claims to detect.

## Honest evidence by channel

| Door | Authenticated principal | Allowed subject claim | What is not claimed |
|---|---|---|---|
| Console control API | Shared console-admin bearer principal | Fixed console subject | Personal identity; loopback as identity |
| Telegram polling | Shared Telegram bot-session principal | Telegram account id from the update | The bot token authenticating the human |
| Telegram webhook | Shared webhook-secret principal | Telegram account id from the update | Telegram personal signature; inability to forge an update |
| Generic webhook | Shared inbound-bearer principal | Mapped sender id from the body | Sender authentication or personal identity |
| Discord Gateway | Shared Discord bot-session principal | Discord account id from `MESSAGE_CREATE` | Civil identity; bot filtering as identity proof |
| Local CLI | Shared local-profile principal | Fixed local operator subject | Personal signature or loopback authentication |

Each shared credential or session maps to one configured requester principal.
Changing the subject claim does not change that principal. A future explicit
administrative binding may name a human principal when stronger evidence
exists; this phase creates no such binding automatically.

## Domain and queue shape

`identity.Resolver` owns immutable boot snapshots of principals, bindings, and
workloads plus private issuer seals. `Resolver.Issuer` returns a channel-bound
issuer. The issuer's `Authenticate` method accepts only a request id and one
allowlisted subject claim. Provider, method, credential class, binding,
principal, generation, instance, issuer, clocks, and claim namespace come
from the issuer configuration.

The adapter binds the resulting opaque value to the inbound envelope through
an unexported envelope slot. `router.DispatchInbound` reads that slot once and
copies it into `inboundWork`. `runBrainWorker` type-asserts the target brain to
the authenticated-brain interface and passes the queued value. A legacy brain
continues through `Brain.Handle` without gaining identity.

`AgentBrain.HandleAuthenticated` starts the existing handler with the queued
ingress bound to that call. Each model tool call puts the same ingress in
`executor.Submission`. `Prepare` snapshots it with the action request.
`Submit` resolves it against the action correlation id, inbound channel,
fixed brain name, and current time before any branch can start.

## Persistence shape

Schema 14 adds the four paper tables with these constraints:

| Table | Required shape |
|---|---|
| `principals` | `principal_id` primary key; finite `kind`; display name; UTC `created_at`; nullable `disabled_at`; positive `revision`. |
| `principal_bindings` | `binding_id` primary key; provider; credential reference only; subject namespace; verified subject; principal foreign key; positive generation; finite status; one equivalent active binding. |
| `identity_evidence_v2` | Evidence id primary key; unique action foreign key with cascade; request; requester, actor, and optional responsible foreign keys to principals; binding foreign key; generation; observed and optional expiry; claims digest; canonical evidence; signing-key foreign key and signature. |
| `principal_events` | Event id primary key; principal foreign key; positive revision; finite kind; canonical event, digest, signing key and signature; unique principal and revision. |

Schema 14 also extends `receipts` with era-aware
`requester_principal_id`, `actor_principal_id`,
`responsible_principal_id`, `identity_status`,
`identity_evidence_digest`, and `identity_snapshot_digest` columns. Existing
rows retain empty values and their original schema version and canonical
bytes. New actions without v2 identity retain the v2 receipt contract. New v2
identity actions use receipt schema v3, whose signed canonical bytes include
all six fields. `GetReceipt` and `ReceiptsByAction` reconstruct each term from
its own stored column; neither infers status from empty attribution. Pruning an
action may cascade-delete the full identity evidence, but its signed receipt
still states the attribution and both digests.

Schema 14 extends `actions` with `identity_version`,
`identity_evidence_digest`, `identity_canonical_evidence`,
`identity_signing_key_id`, and `identity_signature`. Legacy rows default to era
zero and empty snapshots. These columns do not reinterpret history. Every v2
birth writes era two and an exact copy of the signed canonical evidence in the
same transaction as the full evidence row. Receipt construction parses and
verifies that snapshot; it never trusts denormalized identity ids.

The birth-snapshot digest uses SHA-256 over the domain
`korvun.identity-birth-snapshot.v1`, followed by unambiguous length-prefixed
encodings of `identity_version`, `identity_evidence_digest`,
`identity_canonical_evidence`, `identity_signing_key_id`, and
`identity_signature`, in that order. It therefore changes when any stored
snapshot term changes, including the era marker, key id, or signature. A row
is historical legacy only when `identity_version` is zero and all four other
snapshot fields are empty. Every other combination takes the v3 recovery path;
only era two with a complete, valid snapshot receives verified attribution.

`credential_ref` contains a configuration reference such as an environment
variable name or `local_profile`; it never contains the resolved credential.
The canonical evidence uses a fixed struct, not a free-form map. Its fields are
the columns above plus adapter instance, provider, method, credential class,
issuer, subject namespace, and subject claim. Digest and signature are
re-derived from stored canonical bytes on every protected read.

Principal creation and disable append a signed event in the same transaction
as their projection change. A new principal is revision 1. Disable advances
the revision exactly once. This phase has no enable operation.

The latest principal event's canonical projection, revision, digest,
signature, and registered signing key are verified against `principals` during
boot and again inside each durable start or claim transaction. An event insert
failure rolls back its projection. A surviving signed disable event therefore
prevents a raw projection rewind from reactivating its principal.
Missing latest events, changed canonical bytes or digests, unknown verification
keys, and invalid signatures are corruption even when the event and projection
agree with one another. A registered key retired after an object committed
continues to verify that historical object. Retirement only prevents new
identity evidence and principal events from being born under that key; the
active-key check occurs inside each birth transaction.

No-store composition has no durable registry to mutate. It uses the sealed
resolver snapshot created from configuration and validates missing, expired,
foreign-request, foreign-binding, stale-generation, and foreign-instance
ingress in memory. This preserves the current stateless execution contract.
It does not claim protection against a database disable because no database
exists in that mode.

## Pre-test adversarial review

### Literal guarantees

1. No JSON, prompt, sender, display name, channel label, or metadata field can
   create an `AuthenticatedIngress` accepted by the production resolver.
2. Every production message door creates ingress only after its existing
   authentication succeeds.
3. The router queue, not a worker context alone, owns the ingress during the
   asynchronous handoff.
4. Requester, actor, and responsible are independent persisted identities.
5. A committed disable, expired evidence, foreign request, foreign binding,
   stale generation, corrupt signature, or missing evidence prevents a start.
6. No secret-bearing value reaches identity evidence, receipts, metrics,
   structured identity logs, or live-view frames.
7. Migration creates structure only. Historical identity, intent, action,
   evidence, receipt, and approval bytes remain in their original era.
8. A new v2 identity receipt keeps signed attribution and the identity digest
   after its action and full evidence are pruned.
9. No-store execution carries and resolves opaque ingress without claiming
   durable identity evidence or Phase 3's strict-storage guarantee.
10. Crash recovery never needs live identity configuration and still closes a
    v2 action once as `OUTCOME_UNKNOWN`. Verified snapshots retain v3 birth
    attribution; corrupt snapshots are named and cannot become signed false
    attribution.
11. Reload never reissues old work under a new resolver or binding generation.
12. Principal projection changes and their signed events are atomic.
13. A surviving signed disable event defeats a raw projection rewind at boot
    and at the durable start transaction.
14. Every terminal receipt constructor emits v3 for a v2-marked action.
15. Zero marker plus any surviving snapshot field is corrupt v2 identity, not
    legacy. Every v3 signed term round-trips through durable receipt storage.
16. Principal-event authenticity is checked independently of projection
    agreement; coherent forged events remain corrupt.
17. Key retirement separates historical verification from new signing:
    registered retired keys verify committed objects, but cannot sign a new
    identity object.

### Failure taxonomy

- A zero ingress returns `ErrIdentityEvidenceMissing`.
- A request, channel, binding, generation, instance, requester, or workload
  mismatch returns `ErrIdentityBindingMismatch`.
- A non-zero expiry at or before the start instant returns
  `ErrIdentityEvidenceExpired`.
- Malformed canonical bytes, a digest mismatch, an unknown key, or a bad
  signature returns `ErrIdentityEvidenceCorrupt`.
- A v2-marked action with no `identity_evidence_v2` row returns
  `ErrIdentityEvidenceCorrupt`. `ErrIdentityEvidenceMissing` is reserved for a
  zero ingress before any action exists; missing persisted proof never falls
  back to the legacy era.
- A disabled requester, actor, or responsible principal returns
  `ErrPrincipalDisabled`.
- A principal projection that disagrees with its latest signed event returns
  `ErrPrincipalEvidenceCorrupt` before disabled or binding status is judged.
- A driver or transaction failure while reading identity returns
  `ErrIdentityEvidenceUnreadable` with its cause. It is not relabeled as
  missing, invalid credentials, or corrupt evidence.
- Claim precedence is fixed: unreadable store; absent or corrupt evidence;
  principal-history corruption; expired evidence; disabled requester, actor,
  then responsible; inactive or generation-moved binding. Tests that combine
  faults pin this order.
- Identity refusal occurs before a physical tool dispatch. It does not alter
  `tool.CloseStateAfterRun`, close errors, claim errors, or recovery taxonomy.

### Transaction boundaries

- Immediate identity resolution is in memory first. The durable authorized
  record transaction then checks principals and binding, inserts action,
  decision, and signed v2 evidence, and commits before dispatch.
- Approval birth checks and inserts the same identity evidence inside the
  existing action, decision, preview, parameters, and approval transaction.
- Approval claim verifies identity inside the existing claim transaction
  before the conditional parameter purge. Canonical, signature, principal,
  binding, and signing-key reads all use that transaction rather than the
  outer database handle.
- Principal registration and its birth event commit together. Disable and its
  event commit together.
- A signer output is parsed and compared with the pre-sign canonical object
  before insert. The signing key must still be active in the same transaction.
- A terminal v2 identity action records a v3 receipt with signed attribution.
  Historical and non-v2 receipt construction remains on its existing era.
- Recovery reads the immutable v2 attribution snapshot from `actions`, never
  the live resolver or current config. The snapshot is immutable by API, not
  assumed trustworthy: canonical digest and signature are verified before
  attribution. Recovery closes even when full evidence is absent or unreadable
  and emits one v3 `OUTCOME_UNKNOWN` receipt. A corrupt snapshot yields a
  corrupt-status receipt with no attribution.
- Tool invocation stays outside SQLite transactions. Terminal close and the
  existing recovery ownership predicates do not change.

## Cross-Scenarios

The nine named molds own these cross-cutting destructive rows. They are not
optional supplemental tests.

- **Approval ageing and revocation:** AS-ID-03 creates approval evidence valid
  until instant `T`, approves before `T`, advances the claim clock to `T`, and
  calls `ResumeApproved`. Separate real-SQLite, two-connection rows instead
  disable the requester, actor, or responsible, revoke the binding, or advance
  its generation after approval. Each row expects its exact expiry, disabled,
  or mismatch sentinel, zero dispatches, and unchanged approval parameters and
  state. Removing each individual recheck must make its row red.
- **Immediate TOCTOU:** AS-ID-05 resolves ingress, pauses at a committed
  barrier, mutates requester, actor, responsible, binding status, or binding
  generation through the second connection, then releases the start
  transaction. Each check has its own mutation and exact oracle.
- **Signer substitution:** AS-ID-06 compares signer output to the object sent
  for signing and confirms the key is still active inside the transaction.
  Expiry mutation and key retirement are independent evidence attacks.
  Principal birth and disable repeat the trigger, mutation, and retired-key
  attacks against their signed events and projection transaction.
- **Key rotation:** AS-ID-03, AS-ID-05, and AS-ID-08 rotate through the real
  production door after K1 commits an approval, principal event, or crash
  snapshot. Claim, boot/start, and recovery accept K1 for historical
  verification while every new birth requires active K2.
- **Fan-out:** AS-ID-04 proves one ingress can authorize two action births
  without reusing evidence identity or signature.
- **Boot semantics:** AS-ID-08 owns equivalent double boot and incompatible
  existing-binding refusal, transactional migration crash, all evidence-table
  foreign keys, historical migration, receipt retention after pruning, and
  crash recovery for both v2 start states. The recovery rows use child
  processes that exit from inside the fake tool after the production birth or
  claim commit, not direct database fixtures.
- **Authentication cuts:** AS-ID-07 pairs each accepted real door with a
  negative pre-auth path. Its issuer counter is the oracle that no capability
  exists before authentication.
- **Reload:** AS-ID-07 preserves the current router shutdown contract. An old
  worker that acquired a work item observes its sealed R1 ingress. Items still
  queued are cancelled with the old router. Nothing is transplanted into R2 or
  reissued under generation 2.
- **Failure combinations:** AS-ID-03 attacks missing persisted evidence and
  every adjacent precedence pair so error ordering is observable rather than
  an implementation accident.
- **Signed birth snapshot:** AS-ID-08 alters each of the five action snapshot
  terms independently and deletes full evidence before recovery. Era zero with
  any surviving snapshot field remains corrupt v2 identity. The result is one
  durable corrupt-status v3 receipt with the exact encountered-snapshot digest,
  an empty evidence digest, and empty attribution. Reopen verifies the same
  signed bytes; no altered identity is legitimized.
- **All terminal constructors:** AS-ID-08 covers the record-time terminal
  constructor for deny, shadow, unknown tool, and undeclared effect, plus the
  finish/reject/recovery constructor. Leaving either constructor on v2 is red.
- **Projection history:** AS-ID-05 rewinds a disabled projection while keeping
  its signed disable event, then separately makes event and projection agree
  under an invalid signature, corrupts the event key or signature, and removes
  the latest event. Boot and start reject every row.
- **Leak surfaces:** AS-ID-09 mutates evidence, receipt, identity log, metric,
  and serialized SSE construction separately. One combined absence assertion
  is not accepted as proof of all sinks.

### Destructive-test questions

1. The attack target is the authenticated-ingress boundary, the queued cable,
   the transactional recheck, the signer boundary, or an observability sink.
2. The forced dangerous branch is named in the attack matrix and in its
   AS-ID mutation; a test that never reaches that branch is invalid.
3. The expected failure is an exact sentinel, exact zero count, unchanged
   stored bytes, or exact absence of a canary, never a generic non-nil error.
4. The attack matters because otherwise payload claims, stale credentials, a
   database race, or a sink could counterfeit or disclose identity.
5. The evidence level is declared below and cannot be promoted in the canto.

### Planned RED reproductions

Before production edits, each AS-ID test is run by exact name with `-race` and
must fail for its intended missing behavior. The output is saved outside the
repository. After GREEN, every mutation named in the table and Cross-Scenarios
is applied alone, the affected named mold is run with `-race`, the red output
is saved, and the mutation is reverted before the next one. A compilation
failure counts only for the structural queue-field mutation; behavioral
mutations must compile and reach their dangerous branch.

### Known residuals outside Phase 1

- Strict refusal to run without durable identity storage belongs to Phase 3.
- Shared credentials and provider account subjects do not establish personal
  or civil identity.
- Credential rotation, OIDC, mTLS, delegated authority, and principal enable
  operations remain outside this phase.
- Internal in-process event objects may carry message content for existing
  product behavior. AS-ID-09 covers serialized live-view frames, not a claim
  that prompt text never exists inside the process.
- A writer that deletes a signed principal-event tail and rewinds its
  projection to the same earlier revision performs a database rollback this
  self-contained profile cannot detect without an external anchor. The phase
  detects projection edits that disagree with surviving signed history.

  verified attribution survives pruning.

## Decisions folded in

- The current schema makes the migration 13 to 14, not the paper's original
  12 to 13.
- Identity lives in a new dependency-free `internal/identity` package. This
  avoids making message envelopes or SQLite the source of authentication.
- Shared credentials map to shared principals. Subject claims stay evidence
  data and never create humans automatically.
- A private per-resolver issuer seal distinguishes adapter instances. The
  persisted generation describes configured binding generation; the private
  instance seal prevents cross-instance capability reuse within a live
  process.
- Existing legacy APIs remain callable for compatibility, but production app
  composition uses v2 and does not fall back from v2 to legacy.
- Live-view frames are the externally serialized feed checked by AS-ID-09.
  The internal event bus may still hold the existing envelope reference, but
  the v2 ingress is opaque, unexported, and absent from every serialized
  frame.

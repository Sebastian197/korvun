## 2. The design — the published order preserved

The published ladder, `website/docs/reference/operator-cli.md` and its
ES mirror, states the order and pins it for both commands:

> …the chain link to its predecessor, then — when the receipt seals an
> approval digest — **the approval and its tombstone**, and last the
> coherence with the action row. `receipt verify` prints EVERY failure
> it finds, one line each, **in that order**; `korvun ledger check`
> below prints only the FIRST failure of the first receipt that fails.

The draft in the tree inverts it. The design that ships does not, and
the trick is that the LOOKUP and the VERDICT need not happen together.
The block below is indented so that the two switches are visibly
SIBLINGS and not one nested inside the other — the fourth pass read v4's
version as a single switch, and the place where the published order is
won or lost deserves an unambiguous rendering:

```
7b, when SchemaVersion >= 2 and ApprovalDigest != "":

    tomb, tombAt, terr := ApprovalTombstoneByDigest(sealed digest)   // SILENT
    tombstoneProven := terr == nil && tomb.ActionID == r.ActionID

    ── switch 1: the APPROVAL fork, appended FIRST (published order) ──
    switch GetApprovalByAction:
        ErrNotFound:
            action row gone too?
                yes → tombstoneProven      → reconstruction note
                      terr is ErrNotFound  → ambiguous note
                      otherwise            → silent here; switch 2 names it
                no  → fail approval_mismatch (a cascade cannot do that)
        other error:   fail approval_mismatch, WITHOUT the word "unreadable"  [P1-2]
        digest differs: fail approval_mismatch

    ── switch 2: the TOMBSTONE's verdict, appended AFTER (published order) ──
    switch terr:
        nil, tomb.ActionID != r.ActionID → fail tombstone_action_mismatch
        nil                              → proven; nothing to add
        ErrNotFound                      → absence; meaning decided in switch 1
                                           WHEN switch 1 entered its
                                           both-rows-absent leaf, and not
                                           otherwise — see the note below
        *TombstoneFault{Stored}          → fail tombstone_corrupt
        other error                      → fail tombstone_read_failed

7, the action row, LAST — unchanged.
```

**The `ErrNotFound` comment, corrected (P3-5 of the fourth pass).** v4
wrote "its meaning was decided above" without a condition, and that is
false in the state `approval live | action live | tombstone absent`: the
approval fork never enters its `ErrNotFound` leaf, so nothing upstream
decided anything. The silence there is D1, and the design now says which
leaf does the deciding instead of implying that one always did.

**The `is unreadable` lie (P1-2), corrected in this train.** The arm
`case err != nil` catches every error from `GetApprovalByAction`,
including `verifyApprovalStory`'s `decision_outcome_mismatch`,
`decision_policy_mismatch` and the `preview_*_mismatch` family — and the
missing-action-row case of the table below. Calling all of that
"unreadable" is false on a row that reads perfectly. The detail becomes
a sentence true of every class in the arm ("the approval evidence for X
does not hold: …"), which is a PURE MESSAGE change and therefore lands
here, with its mold (T7) and its mutation. Splitting them into distinct
NAMES requires inspecting the error — decision logic — and is FILED to
v0.15.1 with its reproduction.

**What "the action row" means here, before the table can be read.**
`store.Get` is a JOIN — `FROM actions a JOIN action_decisions d ON
d.action_id = a.action_id` (`store.go:1318`) — so its `ErrNotFound`
means "no `actions` row OR no `action_decisions` row". Every earlier
version of this paper read that error as "the action row was pruned",
and the table below inherited the mistake. Three consequences, all
verified by reading and all NEW to v7 (the sixth pass, P1-4):

1. the note the verifier PRINTS, `action_row_absent: row X is gone
   (retention prunes action rows…)`, is false when the `actions` row is
   alive and only its decision row is missing;
2. `receipt.go:290-292` RETURNS on that note, so a missing decision row
   silently disables the outcome and `ActionDigest` comparisons at
   `:297-303` — a check turned off by an absence it mis-reads;
3. the table's "action" column therefore names a JOIN result, not a row.
   It is written that way below, and the state `actions alive +
   decision row deleted` is a row of its own.

None of the three is this cure's radius: they are the same preexisting
class as D5 and they are FILED with it, with the reproduction above.

## 4. Failure taxonomy

`tombstone_corrupt` (read and corrupt at a named column),
`tombstone_read_failed` (not readable for any other reason, never
disguised as history), `tombstone_action_mismatch` (proves the digest,
points elsewhere), absence (not a failure and not a proof of absence —
§1's five forms).

**The dead arm is REMOVED.** v2 kept a named failure for a row selected
by a digest that re-derives a different one. It cannot happen: the
reader contrasts the two before returning, and the SELECT is by that
same column. No mold can force it, and the doctrine's closing clause
governs. Deleting it changes no behavior, which is exactly why keeping
it had no wire behind it.

**`tombstone_read_failed`'s error classes, enumerated.** The `default`
arm absorbs, today: a renamed or dropped table, a corrupt file, an I/O
error, and the SQLITE_BUSY family (a dead context is NOT among them:
`receipt.go:100` and `ledger.go:83` both build `context.Background()`,
which never cancels, so v6 listed a class unreachable through the two
commands it scopes) (`database is locked`
past the DSN's `busy_timeout`). The last one is an AVAILABILITY
transient on a perfectly healthy store, and before the elevation it was
reachable only after a prune; now it is reachable on every v2 receipt
with a digest, next to a running server. Selling it as
`tombstone_read_failed … never disguised as old history` accuses a busy
store of evidence tampering.

CLAUDE.md's Fallback invariant decides this, so it is not a preference:
permanent, invalid, security and policy errors must not silently share
the path of transient availability failures. And the fail-closed rule
decides the outcome: unknown, corrupt or unavailable state fails closed.
A busy store is UNAVAILABLE, so it fails closed — under its OWN name,
saying the check did not run, never under a name that implies tampering.

**The separation is FILED, not implemented — D6's condition bit.** The
director's ruling of 2026-09-08 was conditional in both directions: the
arm ships only if a real `SQLITE_BUSY` is FORCED with two real
connections, and otherwise "no se implementa el brazo: se ficha con la
razón técnica escrita". The forcing succeeded as a CLASS (§7.4b) and
failed as a PATH. Three reasons, each verified, and they are the filing's
content so that whoever implements it later starts past them:

1. **The connection is warm for the whole command.** `OpenReadOnly` sets
   `SetMaxOpenConns(1)` (`store.go:1425`) and nothing else — no
   `SetMaxIdleConns`, no `SetConnMaxLifetime`, no `SetConnMaxIdleTime`
   anywhere in the package. Go's default `MaxIdleConns` is 2, so the one
   physical connection opened by `PRAGMA query_only` survives until
   `Close()` and every read of the ladder rides it. `database/sql` opens
   a replacement only on `driver.ErrBadConn` or after a close.
2. **A warm reader connection PREVENTS the busy rather than suffering
   it.** §7.4b's S2 is the capture: with the reader connection alive the
   writer cannot take `locking_mode=EXCLUSIVE` at all, and the
   `SQLITE_BUSY` lands on the WRITER.
3. **Taking the lock first kills the door, not the ladder.** §7.4b's S1:
   with the lock held before the store opens, `OpenReadOnly` dies on its
   own first statement and the ladder never runs.

Two more findings from the fifth pass belong in the filing, because they
are traps for the implementation this train is not doing:

- **The typed fault does not have a third class today.**
  `TombstoneFault.Error()` (`store.go:446-462`) switches on `Stored`
  alone: a `{Unavailable:true, Stored:false}` value would print
  `tombstone_refused … refused at the door, nothing was written` over a
  read that reached no door and wrote nothing — which is literally the
  P2-5 that R12 cured, under a pin (`tombstone_r12_test.go:642`) that
  would stay green because it exercises only the two old doors. v5 cited
  that same `Error()` as evidence the type "already switches its printed
  class" and then added a class without touching the switch. And "no
  wider public API" was false in its letter: a new exported field on an
  exported type IS new public surface.
- **The classification site must be pinned to the RAW driver error.**
  `isBusyClass` (`store.go:1111`) is `strings.Contains` over
  `err.Error()`, and `ApprovalTombstoneByDigest` wraps with
  `fmt.Errorf("… tombstone with digest %q: %w", digest, err)`
  (`approvals.go:645,648`) where `digest` comes from
  `receipts.approval_digest` — a column the attacker of §5 can write. A
  hand that stores the literal `database is locked` as a receipt's
  digest and then breaks the tombstone table would turn corruption into
  a transient class if the classification ever runs on the WRAPPED
  error. Fail-open wearing fail-closed's clothes. Whoever implements
  this classifies before any `%q` of stored data, and pins that with a
  mold.

Until then the busy family stays inside `tombstone_read_failed`, whose
name says the evidence could not be read. That is narrower than the
Fallback invariant wants and it is declared as a known gap rather than
papered over: §10 carries it as an unresolved risk with its owner and
its target.

**The merge, declared and half-cured here.** Every error from
`GetApprovalByAction` prints under `approval_mismatch`. This train fixes

## 5. Boundaries, blast radius, cost

**Trust boundary and attacker capability** (the fourth pass, P2-7: v4
had no such section, and CLAUDE.md's review law requires one).

- The command runs as the operator, on the operator's machine, over a
  store path the operator's config selects. It is not a network surface.
- The attacker this train models is a hand with DIRECT SQL WRITE access
  to the store file, and nothing weaker: every reproduction in §3 opens
  a second raw connection and issues `UPDATE`/`DELETE`, some with
  `PRAGMA foreign_keys=off`. That capability is strictly greater than
  what any Korvun code path grants.
- What the attacker does NOT have, and the guarantee depends on it: the
  signing key. A hand that also has the key re-signs and re-links, and
  both verifiers exit 0 — R14 proved that by execution, it is
  unchanged here, and it is why A2 is a declared non-claim.
- The store file's own integrity is outside this boundary: a redirected
  config judges another book (R14), and this train does not narrow it.

**Persistence and transaction boundaries.** `verifyReceiptChecks` issues
its reads in AUTOCOMMIT, one at a time, over a pool bounded to one
connection (`SetMaxOpenConns(1)`, `store.go:1425`). There is NO read
transaction and no snapshot: `GetSigningKey`, `ReceiptAt`,
`GetApprovalByAction`, `store.Get` (twice) and `ReceiptsByAction` each
see the store as it is at their own instant, and the cure ADDS a further
read, `ApprovalTombstoneByDigest`, in the same style.

The count of READS is larger than the count of calls, and v5 conflated
them (the fifth pass, P3-Q). `GetApprovalByAction` alone issues five
autocommit statements — the approval id by action (`approvals.go:1048`),
the approval row (`:809`), the canonical preview (`:823`), the `actions`
row (`:865`) and the decision row (`:885`) — so the `actions` row is read
at `:865` and AGAIN at `receipt.go:257` and `:288`, three instants for
one row. The window is wider than "six reads plus one".

That widens a TOCTOU window that already existed, and A18 is the
concrete scenario: the tombstone read returns a healthy row, retention
then prunes the action and cascades its approval, and the approval fork
now takes the both-rows-absent leaf and prints a reconstruction note
narrated from a row read before the world moved. The inverse also
exists: the tombstone reads `ErrNotFound` at one instant and the
ambiguous note is published as a fact about a store that had already
changed. Both are notes, never a false FAILURE, and both are honest
about being unprovable. Wrapping the ladder in a read transaction is the
real cure; it is FILED to v0.15.1 with A18 as its reproduction, and it
is declared here rather than discovered later.

**Writes.** No write statement of its own. That is not "the file is
untouched": `OpenReadOnly`'s own godoc documents that the open creates
WAL sidecars, rewrites the journal header of a store in another mode,
and that the seal is a PER-CONNECTION pragma nothing re-applies to a
replacement connection. The door REFUSES an absent path BY NAME, with an
`os.Stat` that returns before any driver call; what R14 captured is the
TOCTOU window that check leaves — the DSN carries no `mode=ro`, so the
driver's flags are READWRITE|CREATE, and a path removed BETWEEN the
`os.Stat` and the first connection IS created by `sql.Open`.

**Blast radius.** With the published order restored, `failures[0]` is
the approval's name whenever both fire, exactly as documented. What
REMAINS is reachability: a tombstone read error, formerly reachable only
after a prune, is now reachable always — so a store whose
`approval_tombstones` table is renamed away makes `receipt verify` fail
by name (A10) and truncates `ledger check`'s walk at the first v2
receipt carrying a digest (A10b), and a transient lock — which the pool's warm connection makes
unreachable through this command, D6 — surfaces as nothing new. TWO
behaviour changes, not three; both judged correct and fail-closed; both
need molds (T5, T6) and both go in the release notes.

**Cost.** One indexed point lookup per v2 receipt with an approval
digest. Declared, not measured.

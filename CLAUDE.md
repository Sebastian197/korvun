# CLAUDE.md — Korvun

Operating rules for working on this repository. These are non-negotiable.
Read this file in full at the start of every session and follow it strictly.

## Project

Korvun — Kernel for Orchestrated Routing, Versatile Unified Nodes.
A single Go binary acting as messaging gateway + multi-model router +
multi-brain orchestrator, with a configurable dispatch policy engine
(privacy/cost/consensus) driven by a no-code visual builder. Self-hosted,
cross-platform (Linux/Windows/macOS, x86-64/ARM64), same binary from a
Raspberry Pi to the cloud.

Go module path: `github.com/Sebastian197/korvun`


## Engineering mission The goal is not to maximize features, dependencies, abstractions, or architectural complexity. The goal is to evolve Korvun into a production-serious Go AI routing/gateway platform whose engineering can be defended under Staff/Principal-level review. Optimize for, in this order unless a specific context requires otherwise: 1. correctness; 2. privacy and security; 3. data integrity; 4. predictable failure behavior; 5. simplicity; 6. maintainability; 7. testability; 8. observability; 9. measured performance; 10. extensibility; 11. novelty. Korvun's architectural default is a **modular single Go binary**. Preserve that model while evidence says it remains appropriate. Do NOT introduce technologies merely because they are associated with "enterprise" systems. In particular, none of the following is an implicit target architecture: - microservices; - Kubernetes; - Kafka; - Redis; - NATS; - PostgreSQL; - gRPC; - service mesh; - distributed deployment; - generic plugin frameworks. They may be adopted in the future only when a demonstrated problem, trade-off analysis, and an approved design/ADR justify them. Prefer architectural seams that preserve future options without paying today for infrastructure that Korvun does not currently need.

## Non-negotiable workflow (per phase, not just per stage)

Work proceeds in strict granularity: **Stage → Phase → Task**. Do not advance
to a new phase without completing the full cycle below. Do not advance to a new
stage until all its phases are closed. If a task is too large to grasp in one
go, split it.

For every phase:

1. **Verify external docs first.** Before writing ANY code that uses a library,
   framework, SDK, external API, or CI tooling, verify it first — never from
   memory. See "External documentation verification" below for which tool to use
   in each case. If verification isn't possible, stop and say so instead of
   inventing signatures or versions.
2. **Design spec first.** Before writing any code, draft the design spec using
   the `docs/superpowers/specs/TEMPLATE.md` template: fill in Goal, FR-IDs,
   Acceptance Scenarios (Given/When/Then) and Success Criteria; mark anything
   undefined with `[NEEDS CLARIFICATION]` and stop there until it is resolved.
   Do not move on to "Tests first" until the Review Checklist is green.
3. **Tests first (TDD).** Write the test suite that defines the contract BEFORE
   the implementation, and confirm it fails (red). Only then write the minimum
   code to make it pass (green).
   - **The approved red is a contract.** Once a red test suite is reviewed and
     approved, do NOT adjust an already-approved test during the green step
     without asking first — same stop-and-ask pattern as with phantom changes.
     Diagnose first, change only after the "yes".
4. **Implementation.** Only the code needed to make the tests pass.
5. **Quality gate.** `make quality` must be green (lint + vet + tests +
   coverage) over the WHOLE suite, not just the new code, before closing.
6. **Documentation.** Update stage docs, ADRs, and the master document.

## External documentation verification — which tool for what

Never program against an external API, library, or tooling version from memory.
Verify first. The correct verification tool depends on what is being used:

### Code libraries and frameworks → Context7 (mandatory)

For any Go package, npm package, SDK, or framework used in production code
(HTTP routers, Telegram client, SQLite/Postgres drivers, model provider SDKs,
NATS/Redis clients, config libraries, etc.):

- Consult version-specific documentation via Context7 BEFORE writing code
  against it.
- If Context7 is not connected or the docs cannot be verified, STOP and say so.
  Do NOT proceed from memory. This is non-negotiable — wrong function signatures
  recalled from memory cause subtle, hard-to-find bugs.

### GitHub Actions and CI tooling → verify the current tag at source

For GitHub Actions (`actions/checkout`, `actions/setup-go`,
`github/codeql-action`, `anchore/sbom-action`, etc.) and other CI tooling,
Context7 is NOT the right tool (it covers code libraries, not Action tags).
Instead:

- Verify the current stable tag at the Action's own GitHub repository
  (its `/releases` page) or the GitHub Marketplace, using WebSearch/WebFetch.
- Do NOT guess tags from memory. If web access is unavailable, say so and pin
  to a known major tag with a `# TODO: verify action version` comment, rather
  than silently assuming.
- Prefer pinning Actions to a full commit SHA (most secure) or at least a
  fixed major tag (e.g. `@v4`), never a floating ref.

### General principle

The rule is always the same — never invent versions or signatures. Only the
*tool* changes: Context7 for code libraries, the source repo/marketplace for
Action tags.

## Sources of truth — CRITICAL 
Never work from memory when the repository can answer the question. For claims about current Korvun behavior, use the following precedence: 1. current source code; 2. executable tests and their observed results; 3. current configuration and workflows; 4. `go.mod` / `go.sum` and lockfiles; 5. accepted ADRs; 6. approved design specs; 7. current architecture/operations documentation; 8. `docs/HANDOFF.md`; 9. graphify; 10. historical documentation. Graphify is the mandatory navigation map, but source code is the final authority for actual behavior. A graph, document, ADR, stage report, or handoff may be stale. For any material architectural, security, privacy, lifecycle, concurrency, or data-flow claim: 1. use graphify to locate and understand the relevant area; 2. inspect the actual source; 3. inspect relevant tests; 4. execute verification where necessary. Never claim that something is absent without checking first. Never claim that something is implemented merely because documentation mentions it. When something cannot be established from available evidence, state that explicitly instead of guessing.

## AUDIT / REVIEW MODE 
Audit, investigation, architecture review, diagnosis, threat modeling, baseline collection, and code review are READ-ONLY unless the current task explicitly authorizes edits. In audit/review mode: - do not modify source; - do not modify tests; - do not modify docs merely to record discoveries unless explicitly requested; - do not create commits; - do not fix findings while discovering them; - do not silently clean up unrelated issues. The sequence is: DISCOVER → VERIFY → CLASSIFY → REPORT Implementation happens only in a subsequent authorized task. ### IMPLEMENTATION MODE When implementation is explicitly authorized, the sequence is: DISCOVER → DEFINE → DESIGN → RED → GREEN → VERIFY → REVIEW → DOCUMENT Do not mix unrelated findings into the implementation scope.

## Scope control — CRITICAL 
Do not fix unrelated problems discovered while working on the current task. When an out-of-scope problem is discovered: 1. record the evidence; 2. classify whether it blocks the current task; 3. if it blocks the task, report it before proceeding; 4. if it does not block the task, add it to the appropriate backlog/findings mechanism and continue the authorized scope. Avoid drive-by refactors. Avoid opportunistic dependency upgrades. Avoid formatting unrelated files. Avoid changing public behavior not covered by the current design. A smaller correct diff is preferred over a broad "cleanup" diff.

## Work state semantics 
Use these states when reporting substantial engineering work: - DISCOVERED - PLANNED - IN_PROGRESS - IMPLEMENTED - VERIFIED - ACCEPTED - BLOCKED - REJECTED The meanings are strict: `IMPLEMENTED != VERIFIED` Code existing in the tree does not prove correctness. `VERIFIED != ACCEPTED` Passing the author's local checks does not replace review against the acceptance criteria. Do not describe work as fixed, safe, race-free, secure, performant, production-ready, or enterprise-ready without evidence appropriate to that claim.

## Independent review mindset 
After implementation, review the result as if you did not author it. The review goal is not to confirm that the implementation looks reasonable. The goal is to try to disprove that the task is complete. Review at least: - semantic correctness; - error paths; - regressions; - context cancellation; - goroutine/resource lifecycle; - race/deadlock risks; - privacy invariants; - security boundaries; - unbounded resource growth; - public compatibility; - unnecessary abstractions; - dependency impact; - performance claims; - documentation accuracy. If the evidence does not satisfy the acceptance criteria, report the task as REJECTED or BLOCKED, not as complete. Never weaken an approved test merely to make an implementation pass.

## Invariant-driven engineering — CRITICAL 
Prefer system invariants over collections of happy-path examples. Identify, document, and test important invariants whenever the subsystem has security, privacy, routing, lifecycle, or resource-management consequences. ### Privacy invariant Private data may flow only to explicitly trusted sinks. "Private" must not be interpreted solely as "do not call a cloud model". Potential egress includes: - models; - providers; - tools; - logs; - traces; - metrics; - telemetry; - error reporting; - crash reporting; - control APIs; - persistence; - attachments or exports. When private execution is enabled, every possible egress path must preserve the policy. ### Control API invariant Unauthenticated control surfaces must be loopback-only: `NO AUTH <=> LOOPBACK ONLY` If a control API can bind to a non-loopback address, the design must explicitly address authentication, authorization, transport security, and auditability. ### Cancellation invariant When a context is cancelled, downstream work must eventually stop and release owned resources. ### Resource-bound invariant No user-controlled or externally-driven path may create unintended unbounded growth in: - goroutines; - queues; - maps; - caches; - message history; - attachments; - request bodies; - response bodies; - provider fan-out; - retries; - metric label cardinality. ### Fallback invariant Fallback must be driven by explicit error semantics. Permanent/invalid/security/policy errors must not silently trigger the same fallback behavior as transient availability failures unless the design specifically defines it. ### Consensus invariant Consensus behavior must define: - minimum success semantics; - partial failures; - slow members; - cancellation; - timeout; - quorum when applicable; - reducer behavior; - cost bounds; - what happens when the required result cannot be produced. Critical invariants should be enforced through deterministic tests, property-based tests, fuzzing, or integration tests as appropriate.
